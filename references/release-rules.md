# 回归与交付

## 一、回归的触发条件

所有生效计划里的有效节点都 `completed` 之后。`df.py regression-check` 会检查：

- 有没有 `pending` / `ready` / `in_progress` / `needs_review`
- 有没有 `blocked` / `failed`
- 已完成节点的证据是否齐全（报告、测试、退出码）
- 每条 active 需求是否都有已完成节点覆盖

**有阻塞就不能宣称可以交付。** 这句话要真的执行，不是写在文档里好看。

## 二、回归清单

按项目实际技术栈执行，不适用就写 `not_run` + 原因。

| # | 项 | 怎么算通过 |
| --- | --- | --- |
| 1 | 编译 / 构建 | 退出码 0，产物存在 |
| 2 | 单元测试 | 全绿，无跳过 |
| 3 | 集成测试 | 全绿 |
| 4 | 核心业务链路 | 端到端跑通，数据正确 |
| 5 | 接口契约 | 字段、类型、错误码符合约定 |
| 6 | 数据一致性 | 对账公式成立 |
| 7 | 权限 | 未登录/越权被拒 |
| 8 | 数据库脚本 | 能正向执行，回滚有说明 |
| 9 | 需求验收项 | 逐条对照需求基准 |

## 二·五、回归报告必须是机器可读的

Markdown 是给人看的，不能作为交付依据——"报告存在"和"测试通过"是两件事。

`regression/final-report.json` 是事实来源，每个检查项至少包含：
`check_id` / `name` / `required` / `status` / `command` / `exit_code` / `executed_at` /
`evidence` / `notes`。

| 状态 | 含义 | 要求 |
| --- | --- | --- |
| `passed` | 实际执行并通过 | 必须有命令、退出码 0、证据 |
| `failed` | 执行了但失败 | 必须写原因 |
| `not_run` | 没执行 | 必须写原因，且不能算通过 |
| `skipped` | 不适用 | 必须写原因 |

整体状态由检查项推导，不能自己填：

```
任一必需项 failed            → failed
任一必需项 not_run / skipped → not_run
全部必需项 passed            → passed
```

声明值与推导值不一致，`regression-import` 直接拒绝。

`config/quality-gates.yaml` 的 `required_checks` 列出必须存在的检查项；
缺项等于"没检查"，拒绝导入。不适用的项要显式 `skipped` + 原因，不能直接省略。

`release` 读 JSON 并重新校验，不看 Markdown 的措辞。旧项目只有 Markdown 时，
`release --legacy-regression` 是明确的降级开关，会在项目档案里留痕。

## 三、问题定位

发现问题时，不要直接改代码。先定位：

```
问题 → 对应需求（REQ-xxx）→ 对应节点（DF-xxx）→ 该节点的执行报告 → 实际代码
```

然后决定：

- 是实现 bug → 修，重跑受影响测试
- 是需求理解错 → 回到需求基准，可能要开 CR
- 是测试本身错 → 修测试，说明为什么
- 是环境问题 → 记录，不算通过

**没有定位依据就改其他模块，是最危险的操作。**

## 三·五、交付状态机

```
in_progress ──(全部节点完成)──> regression
                                    │
                                    │ release（生成报告 + 查门槛）
                                    ▼
                            release_candidate
                                    │
                                    │ release-ready（复核门槛）
                                    ▼
                             release_ready
                                    │
                                    │ release-accept --by <人>
                                    ▼
                                accepted
```

四个状态对应四件事，不能合并：

| 状态 | 含义 | 谁产生 |
| --- | --- | --- |
| `regression` | 正在做全量回归 | `regression-check` |
| `release_candidate` | 交付报告已生成，**未**交付 | `release` |
| `release_ready` | 交付条件已满足，等待人验收 | `release-ready` |
| `accepted` | 用户已明确验收 | `release-accept --by` |

`release` 每次都会重新计算门槛：节点完成度、证据齐全、回归结论 `passed`、需求覆盖。
门槛不过时**仍然生成报告**（便于对照修），但退出码 1，状态停在 `release_candidate`。

回归结论从 `final-report.json` 读取（旧项目可加 `--legacy-regression` 读 Markdown 的
`结论：passed` 行）。没有结论行、写成 `failed`，或者必需检查项没跑，都进不了 `release_ready`。

**`accepted` 是终态。** 到达之后 `start` / `sync` / `accept` / `retry` / `regression-check` /
`release` / `release-ready` 全部拒绝执行（退出码 2），`regression-check` 也不能把状态改回
`regression`。要继续开发只能走变更：`change-new` → `change-apply`（新计划 + 状态回 `in_progress`）。

## 四、交付报告的诚实原则

必须区分四类，不能混：

| 状态 | 含义 |
| --- | --- |
| ✅ 已实际验证通过 | 有命令、有退出码、有结果 |
| ⚠️ 已实现但未验证 | 代码写了，但没有自动化验证或没跑 |
| ❌ 尚未实现 | 计划里有，实际没做 |
| 🚧 已知限制 | 能做到但本期不做（如多实例、过期机制） |

`df.py release` 会自动把节点分成"已验证 / 已实现未验证 / 未实现"三类。
不要手动把它们都写成"已完成"。

## 五、交付报告必含

1. 项目概述与范围（做了什么、没做什么）
2. 需求完成情况（逐条，带覆盖节点）
3. 任务完成情况（逐条，带测试证据）
4. 主要代码变更
5. 数据库脚本（有就列，没有写"无"）
6. 构建与测试结果（真实命令与结果）
7. 核心链路验证结果
8. 部署说明（能照着做）
9. 配置项清单（不含真实密钥）
10. 验证状态分类
11. 已知问题与风险
12. 最终验收（谁确认、什么时候）

## 六、部署说明的最低要求

- 依赖环境与版本
- 安装/构建命令
- 启动命令与端口
- 配置项：名称、是否必填、默认值、影响
- 数据初始化/迁移步骤
- 健康检查方式
- 回滚步骤

写"参考 README"不算部署说明。

## 七、交付前最后三问

1. **新人能照着文档跑起来吗？** 不能就补文档。
2. **出问题能定位到节点吗？** 不能就补追踪关系。
3. **有没有把"没验证"写成"已验证"？** 有就改回来。

## 八、交付之后

- 用户的验收意见记进 `decisions.md` 或新的 CR
- 遗留问题要么开节点，要么写进"已知问题"
- 不要"交付即失联"：上线后的问题仍然要能追溯到需求和节点
