# 需求变更管理

## 一、变更不是改计划

改计划是"把 v1 的某个节点改一下"。变更管理是"**生成 v2，保留 v1，说清谁受影响**"。

区别在于可追溯：三个月后有人问"当时为什么把余额校验改成可用额度"，
你要能翻出 CR-001 和它对应的 v1→v2 差异。

## 二、流程

```
用户提出变更
  → change-new（建 CR 记录）
  → 影响分析（读需求/计划/状态/报告/代码）
  → 写 impact-assessment.md
  → 生成新版需求基准 + 新版计划（draft）
  → 用户确认影响范围
  → change-apply（旧计划 superseded，新计划 active）
```

**分析阶段绝对不要改当前生效计划。** 用户还没确认，改了就是既成事实。

## 三、影响分析怎么做

### 3.1 四份输入，缺一不可

1. 当前需求基准（`confirmed-requirements-vN.md`）
2. 当前计划与节点状态（`backlog-vN.json`）
3. 需求追踪关系（`traceability.json`）
4. **实际代码**（不是任务名）

只看任务名判断影响，是最常见的错误。"这个节点叫账户服务，改余额肯定影响它"——
也许它其实没用到那个字段。要去看代码。

### 3.2 五个动作

| 动作 | 含义 | 处理 |
| --- | --- | --- |
| `reusable` | 完全不受影响 | 原样带进新计划，状态保持 completed |
| `modify` | 需要改代码 | 新计划里重建为 `ready`，remark 写返工原因 |
| `add` | 需要新增节点 | 新节点，接进正确依赖位置 |
| `deprecate` | 不再需要 | 标 `superseded`，不要删除 |
| `review` | 信息不足 | 先评估，结论落成上面四种之一 |

`review` 不是终点。评估完必须给出结论，不能挂着。

### 3.3 顺着依赖链检查

改了一个已完成公共能力的接口/数据结构，必须检查**所有下游**：

```
DF-002 数据模型改了 frozen_delta
  → DF-003 仓储（用到 LedgerEntry）→ 要不要重测？
  → DF-004 服务（用到 LedgerEntry）→ 要不要重测？
  → DF-006 集成 → 必须重跑
```

检查方法：搜代码里对这个接口/字段的引用，而不是看依赖图就完事。

### 3.4 兼容性三问

1. **数据**：旧数据还能读吗？需要迁移吗？迁移能回滚吗？
2. **接口**：调用方会不会挂？是语义收紧还是放宽？
3. **行为**：同样的输入，结果会不会变？变了要通知谁？

## 四、版本化规则

| 对象 | 规则 |
| --- | --- |
| 需求 | `confirmed-requirements-vN.md` 只增不改 |
| 追踪表 | `traceability-vN.json` 保留历史，`traceability.json` 指向当前 |
| 计划 | `backlog-vN.json` 只增不改；旧版本标 `superseded` |
| 看板 | `board-vN.md` 由对应 JSON 渲染 |
| 报告 | 返工前归档到 `nodes/<ID>/history/` |
| 变更 | `changes/CR-00X/` 独立目录 |

## 五、保护已完成的工作

这是变更管理最容易做错的地方。

- **不受影响的 completed 节点不要重跑。** 重跑浪费时间，还会引入新风险。
- **受影响的 completed 节点，在新版里重建为 `ready`**，不要直接改成 `in_progress`
  （还没人开始做）。旧版本里的 completed 记录保留，那是历史事实。
- **不要删除废弃节点**，标 `superseded` + `superseded_by`。
- 返工节点的旧报告自动归档，新报告重新生成。

## 六、变更的风险评估

至少评估四项：

| 风险 | 问什么 |
| --- | --- |
| 数据 | 结构变了要不要迁移？旧数据读得出来吗？ |
| 兼容 | 已有调用方会不会挂？ |
| 范围 | 会不会引发连锁返工？返工几个节点？ |
| 回滚 | 上线后发现不对，怎么退？ |

高风险变更（改核心数据模型、改对外接口、涉及已上线数据）必须让用户明确确认，
不能"评估完直接应用"。

## 七、反模式

| 反模式 | 后果 |
| --- | --- |
| 直接改 backlog-v1.json | 历史丢失，无法追溯 |
| 变更后把所有节点标 ready 重跑 | 浪费，且可能改坏已验证的东西 |
| 只改需求文档不改计划 | 需求和计划脱节，验收时对不上 |
| 影响分析只看任务名 | 漏掉真正受影响的下游 |
| `review` 挂着不结论 | 计划里留了个黑洞 |
| 变更不写原因 | 三个月后没人知道为什么改 |
