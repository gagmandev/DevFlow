# 需求分析

## 目标

把一份人写的需求，变成**可编号、可追踪、可验收**的需求条目。
分析完成的标志不是"我读懂了"，而是"每条需求都有编号、来源和验收标准"。

## 一、十五个维度

逐项过，缺的写"需求未提及"，不要留空、不要脑补。

| # | 维度 | 要问自己的问题 | 输出到 |
| --- | --- | --- | --- |
| 1 | 项目目标 | 解决什么问题？成功长什么样？ | 建设目标 G-xxx |
| 2 | 系统边界 | 什么归我做，什么不归？边界怎么交互？ | 系统边界 |
| 3 | 业务角色 | 谁用？各自能做什么、不能做什么？ | 角色与权限 |
| 4 | 业务流程 | 主流程几步？分支在哪？ | 流程图 |
| 5 | 核心业务规则 | 哪些规则算错了就是事故？ | 业务规则 BR-xxx |
| 6 | 功能需求 | 每个功能点的输入、输出、异常 | REQ-xxx |
| 7 | 非功能需求 | 性能、并发、可用性、安全、兼容性 | 非功能表 |
| 8 | 数据模型 | 实体、字段、约束、归属、保留 | 数据需求 |
| 9 | 外部依赖 | 依赖谁？它挂了怎么办？ | 外部依赖表 |
| 10 | 技术约束 | 必须用什么、禁止用什么、要遵循什么规范 | 技术约束 |
| 11 | 权限要求 | 谁能看、谁能改、越权怎么处理 | 角色与权限 |
| 12 | 异常场景 | 参数错、并发、超时、重复提交、脏数据 | 异常与边界 |
| 13 | 数据一致性 | 哪些数据必须同时对？对不上怎么修？ | 数据需求 |
| 14 | 并发与性能 | 峰值多少？会不会抢同一份数据？ | 非功能表 |
| 15 | 验收标准 | 怎么判断做完了？ | 每条需求的 acceptance |

## 二、需求编号

- 格式 `REQ-001`，三位起，按出现顺序分配。
- **编号一旦分配不复用**，需求删除时标 `status: removed`，不要回收编号。
- 变更产生的新需求继续往后编（`REQ-009`），不要插空。
- 每条必须能回答：来自哪份文件的哪一节（`source`）。

## 三、验收标准怎么写

合格：

- `1999 分（19.99 元）奖励 19 积分`
- `余额不足时抛 InsufficientBalance，且余额与流水都不变`
- `20 线程各扣 1 分、余额 10 分时恰好 10 次成功`

不合格：

- `功能正常`
- `性能良好`
- `代码规范`

判断方法：**换一个人来验收，能不能得出同样的结论。** 不能就重写。

## 四、歧义分类

### A 类：必须确认

不问清楚就不能拆任务，也不能生成需求基准。

- 核心业务规则与计算口径（比例、取整、优先级、边界值）
- 主流程的先后顺序与状态流转
- 系统边界（这件事到底归谁做）
- 数据归属与唯一性
- 第三方系统依赖及其不可用时的行为
- 重大技术选型（决定部署形态、数据存储）
- 权限与安全规则
- 数据一致性要求（强一致 / 最终一致）

### B 类：建议确认

给默认值，用户不反对就采用，写进决策记录。

- API 命名与路径风格
- 字段命名与返回结构
- 错误码规范
- 日志格式与级别
- 通用异常处理方式
- 分页默认值与上限

### C 类：自主决策

不影响业务结果，按项目现有规范决定，记录在 `decisions.md`。

- 内部函数拆分
- 私有字段命名
- 局部算法选择
- 测试文件组织方式

## 五、提问的质量

一个问题包含五要素：

1. 原始描述（需求文档里的原话，或"文档未提及"）
2. 为什么必须确认（不问会导致什么返工）
3. 可能影响（数据模型 / 接口 / 权限 / 性能）
4. 推荐方案（带理由）
5. 备选方案

**一次问完，最多 5 个。** 超过 5 个说明需求本身太糙：先按默认值出一版，
让用户对着具体方案改，比让他回答 20 个抽象问题有效。

不要问的问题：配色、文案措辞、按钮位置、用什么 UI 库、目录叫 `src` 还是 `app`。

## 六、多模态输入

| 输入 | 处理 |
| --- | --- |
| Markdown / TXT | 直接读，注意标题层级与表格 |
| PDF / Word | 提取正文；表格和批注不能丢 |
| 原型图 | 提取页面、字段、交互、状态；看不清就说看不清 |
| ER 图 | 提取实体、字段、关系、基数；与文字描述冲突时**以文字为准并提问** |
| 架构图 | 提取模块、调用方向、外部系统 |
| Mermaid | 直接解析节点与边 |
| 现有代码 | 只提取"现状"，不要当成"需求" |

看不清的图不要猜。明确告诉用户："这张图的分辨率不足以辨认字段名，请提供清晰版本或文字描述。"

## 七、常见坑

1. **把实现当需求**：需求说"用 Redis 存会话"，真实需求可能是"会话要能跨实例共享"。追问一层。
2. **漏掉异常路径**：只写主流程的需求，落地时一定会在异常分支上卡住。
3. **验收标准写成任务**："实现登录接口"不是验收标准，"错误密码返回 401 且不锁定账号"是。
4. **假设当事实**：把自己的推测写进需求基准。所有推测都要在 `clarification.md` 里有出处，或标为假设。
5. **过早细化**：需求阶段就决定表结构字段名，后面一改全崩。需求阶段定"要存什么"，不定"字段叫什么"。
