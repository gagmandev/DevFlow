# 任务拆解

## 目标

拆出来的每个节点，都应该满足：**一个 Agent 一次能做完、一句话能验收、改动的文件边界清楚。**

拆解不是把需求切碎，是把**交付单元**切出来。

## 一、五个阶段

| 阶段 | 判断标准 | 典型内容 |
| --- | --- | --- |
| Foundation | 后面所有节点都依赖它 | 框架、目录、配置、数据库结构、迁移、日志与异常基础设施 |
| Shared | 多个业务节点共用 | 实体、DTO、仓储、数据访问、鉴权、统一返回、公共组件 |
| Business | 直接实现一条业务规则 | 账户、订单、流水、支付、抽奖 |
| Integration | 验证多个节点能否拼起来 | 联调、核心链路、接口契约、一致性、权限联调 |
| Release | 让人能接手 | 脚本整理、部署配置、交付文档、最终验收 |

## 二、一个节点的八个字段

| 字段 | 要求 | 反例 |
| --- | --- | --- |
| 目标 | 一句话说清交付什么 | "优化代码" |
| 输入 | 必须读哪些文件/产物 | "看情况" |
| 前置依赖 | 哪些节点必须先完成 | 漏写隐含依赖 |
| 修改范围 | `files_scope`，精确到文件或目录 | "整个 src/" |
| 实现要求 | 关键接口、数据结构、边界处理 | 只写"实现功能" |
| 验收标准 | 可判断真假，至少一条 | "功能正常" |
| 测试方案 | 要覆盖哪些场景、跑什么命令 | "写测试" |
| 交付物 | 产出哪些文件/能力 | 没写报告文件 |

## 三、粒度的三个判据

1. **能独立验收**：验收标准只涉及这个节点的产出，不依赖别的节点"顺便做完"。
2. **能独立回滚**：出问题时能单独撤掉，不牵连一片。
3. **文件边界清楚**：`files_scope` 能列出来，且和其他并行节点不重叠。

经验值：

- 涉及文件 ≤ 8 个
- 一个节点一次会话能完成
- 单版本节点数 5–30 个比较健康；超过 40 个通常拆太细或需求太大

**不要按代码行数拆。** 一个节点可以改 6 个文件，只要它们构成一个完整实现单元。
也**不要为了减少节点数**把无关功能塞一起。

## 四、按功能域拆，不按技术层拆

对的：

- `账户服务：开户 / 签到 / 奖励 / 扣减 / 余额`
- `流水查询与运营视图`
- `订单创建与支付回调`

错的：

- `写所有 service`
- `写所有 Controller`
- `写所有单元测试`

按技术层拆的后果：每个节点都要等所有实体就绪，无法并行；验收时也说不清"这个节点做完了"是什么状态。

## 五、依赖推导

常见的边：

```
数据库结构 → 实体/DTO → 仓储 → 业务服务 → 接口 → 集成验证
公共能力（异常、鉴权、返回结构） → 所有业务节点
```

判断"要不要加这条边"的方法：**如果 A 没做完，B 能不能真的开始写？**
不能就是有依赖；能但会返工，也要加。

容易漏的依赖：

- 两个节点都改同一个配置文件
- 后一个节点要用前一个节点定的错误码
- 后一个节点的测试要跑前一个节点的数据
- 后一个节点依赖前一个节点做的数据迁移

## 六、并行判定

六个条件**全部**满足才并行：

1. 前置依赖已完成，或共享同一个已完成依赖
2. 彼此没有直接依赖
3. `files_scope` 不重叠
4. 接口契约已确定（不是"大概这样"）
5. 不涉及同一张表/同一份数据的结构变更
6. 不会产生互相覆盖的实现（比如两个节点都改同一个基类）

拿不准就不并行。串行慢一点，冲突要重做。

并行组建议不超过 3 个节点——人盯不过来，冲突排查成本指数上升。

## 七、优先级

`P0` 只给"不做完，所有人都动不了"的事。

- 项目骨架通常 P0（没它谁都开不了工）
- 数据模型通常 P0（实体不定，业务没法写）
- 业务节点多数 P1/P2
- 文档、优化、非关键脚本 P2/P3

**不要把整个 Foundation 都标 P0。** 优先级失去区分度，就等于没有。

## 八、拆完自查

1. 随便挑两个没有依赖关系的节点，`files_scope` 有重叠吗？有 → 边界没划清。
2. 每个节点的验收标准，能不能只看这个节点的产出就判断？不能 → 依赖没写全或粒度不对。
3. 有没有节点的目标是"重构"、"优化"、"整理"？有 → 不可验收，重写。
4. 把所有节点的 `outputs` 加起来，能不能覆盖需求？缺的 → 漏了节点。
5. 有没有节点既不属于任何阶段、也不对应任何需求？有 → 可能是臆想出来的工作。

## 九、一个合格节点长什么样

```json
{
  "node_id": "DF-004",
  "node_name": "账户服务：开户 / 签到 / 奖励 / 扣减 / 余额",
  "phase": "Business",
  "type": "business",
  "priority": "P1",
  "description": "实现 WalletService 的核心写路径，并保证并发不超扣。",
  "requirement_ids": ["REQ-001", "REQ-002", "REQ-003", "REQ-004", "REQ-006"],
  "dependencies": ["DF-003"],
  "parallelizable": true,
  "parallel_group": "A",
  "acceptance_criteria": [
    "重复开户幂等，不产生第二个账户",
    "1999 分订单奖励 19 分，同一订单号只入账一次",
    "余额不足抛 InsufficientBalance，余额与流水均不变"
  ],
  "files_scope": ["src/points/service.py", "tests/test_service.py"],
  "test_strategy": ["开户幂等", "签到幂等", "奖励取整", "余额不足无副作用"],
  "outputs": ["src/points/service.py", "tests/test_service.py"]
}
```

注意它没有写"代码要优雅"这种没法验收的东西。
