# 依赖与并行

## 一、DAG 是硬约束

任务依赖必须是有向无环图。出现环，说明需求理解或分层出了问题，**必须修正，不能带病出计划**。

`df.py plan-import` 会在导入时检测环并拒绝；`dependency_check.py` 会打印环的具体路径。

常见环的成因：

| 环 | 真实原因 | 修法 |
| --- | --- | --- |
| A 依赖 B，B 依赖 A | 两个节点其实是一个交付单元 | 合并 |
| A→B→C→A | 接口契约没定，互相等对方 | 先抽一个"定义契约"的节点 |
| 数据模型与服务互依赖 | 边方向搞反了 | 数据模型在前 |

## 二、边的类型

| 类型 | 例子 | 能不能省 |
| --- | --- | --- |
| 结构依赖 | 表结构 → 实体 | 不能 |
| 分层依赖 | 仓储 → 服务 → 接口 | 不能 |
| 契约依赖 | 接口定义 → 调用方 | 不能 |
| 业务流依赖 | 扣减能力 → 抽奖 | 不能 |
| 公共能力依赖 | 异常体系 → 所有业务 | 不能 |
| 数据一致性依赖 | 账户变更 → 对账 | 视情况 |
| 测试依赖 | 集成测试 → 所有被集成节点 | 不能 |

## 三、并行六条件

见 `task-decomposition.md` 第六节。这里补充怎么**验证**：

1. **文件冲突**：把两个节点的 `files_scope` 取交集。空集才安全。目录级 scope 要展开比较。
2. **契约未定**：如果 B 调用的接口签名还在"待定"，不能并行——B 会写错，A 一改 B 就废。
3. **数据冲突**：两个节点都改同一张表结构 → 必须串行，否则迁移脚本会打架。
4. **隐式共享**：两个节点都改同一个工具函数/基类 → 视为文件冲突。

`validate.py` 会对同组节点的 `files_scope` 重叠给警告。**警告不是可以忽略的**，要么拆开，要么改成串行。

## 四、分层与关键路径

`dependency_check.py` 会算"最长路径分层"：

```
L1: DF-001
L2: DF-002
L3: DF-003
L4: DF-004, DF-005, DF-008
L5: DF-006
L6: DF-007
```

同一层的节点之间**必然没有依赖**，是并行候选（还要过文件冲突检查）。
关键路径（最长链）决定项目最短工期——想加速就优化关键路径上的节点，优化别处没用。

## 五、永远不会 ready 的节点

三种情况，`dependency_check.py` 会报：

1. 依赖了一个不存在于本计划的节点
2. 依赖了 `superseded` 或 `cancelled` 的节点
3. 处在环里

发现后不要"手动标 ready"绕过，要修依赖或补节点。

## 六、变更后的依赖维护

变更产生新版计划时，依赖关系要重新检查：

- 新增节点要接进正确位置（不能挂在最后"凑数"）
- 被废弃节点的下游要改指向替代节点
- 已完成节点的返工，会让它的下游出现"已完成但依赖未完成"的状态

最后这种情况是正常的（历史完成是真的），但**必须逐个人工确认是否需要重测**，
并在节点 `remark` 里写明理由。`validate.py` 会对没写理由的给警告。

## 七、反模式

| 反模式 | 后果 |
| --- | --- |
| 所有业务节点都依赖一个"万能基础节点" | 基础节点变成瓶颈，一改全动 |
| 为了并行强行去掉真实依赖 | 联调时接口对不上，返工 |
| 并行组里放 5 个以上节点 | 冲突排查成本爆炸 |
| 用"顺序执行"冒充并行 | 看板失真，工期估算错误 |
| 依赖写"DF-001~DF-005"这种范围 | 无法机器校验，等于没写 |
