# 08 · 需要决策的问题

> 每条包含：为什么必须由人决定、可选方案、建议、影响面、是否阻塞后续阶段。
> 本阶段不替产品做决定，也不把建议当成已实现。

## D-01 计划变更是否一律走 CR？

- **背景**：现状允许 `plan-import` + `plan-activate` 换计划，不需要 CR（`df.py:522`、`587`）。
  这是 INV-008 未实现的直接原因。
- **选项**：
  - A. **一律走 CR**：v>1 必须有 `based_on.change_id`；首次计划（v1）例外。
  - B. 允许 `--replan`（记录 reason + by），不要求 CR。
  - C. 维持现状（不推荐）。
- **建议**：A 为主，B 作为显式逃生口（写 `based_on.kind="replan"`，仍然留痕）。
- **影响**：所有"重新拆任务"的流程都要先开 CR；文档/示例需同步。
- **阻塞**：阻塞 INV-008 修复与"无 CR 换计划"测试。

## D-02 需求基准用"内容指纹"还是"全文版本化"？

- **背景**：`confirmed-requirements-vN.md` 目前无任何完整性保护。
- **选项**：
  - A. `req-confirm` 记录 sha256 到 `project.requirement_baseline`，回归/交付校验。
  - B. 由 CLI 生成基准文档（从 traceability 渲染），Agent 不再直接写。
  - C. 把基准文档纳入 Git 提交并要求签名（重）。
- **建议**：先 A（成本最低、能堵住暗路）；B 作为中期方向（彻底消除"Agent 写正式数据"）。
- **影响**：A 只加校验；B 会改变"谁写基准文档"的协作方式，需要改 SKILL 与模板。
- **阻塞**：阻塞 INV-002 / INV-020。

## D-03 Git 变更如何归属到节点？

- **背景**：`git_changes_since` 减掉 baseline dirty 文件（`dfcore.py:993`），并行节点还会互相污染。
- **选项**：
  - A. baseline 逐文件指纹比较（改动小，能解决"开工前 dirty 又被改"）。
  - B. 每节点独立 `git worktree`，验收时合并（隔离彻底，运维成本高）。
  - C. 要求节点开工前工作区必须干净（最严格，体验差）。
- **建议**：A 必做；B 作为"并行 > 1 个 Agent"时的推荐部署方式（写成部署约束，不必进 CLI）。
- **影响**：A 影响 `git_snapshot` 的数据结构（加 `dirty_fingerprints`，向后兼容）；B 影响宿主/CI 编排。
- **阻塞**：阻塞 INV-012 与"并行归属"相关测试。

## D-04 ignored 文件怎么处理？

- **背景**：`.env`、构建产物、被 `.gitignore` 的配置，当前既不在报告也不在 Git 变更里。
- **选项**：
  - A. production 下 `deny`：检测到 ignored 文件变化就阻断。
  - B. `allowlist`：只允许特定目录（`dist/`、`coverage/`）。
  - C. `off`：不管。
- **建议**：production 用 B（`allowlist` 默认只允许构建产物），development 用 C；
  比 A 更实用（A 会被噪音淹没）。
- **影响**：需要新增 `node.ignored_allowlist` 或全局配置；`git status --ignored` 可能很慢。
- **阻塞**：阻塞 INV-011 的"ignored 盲区"修复。

## D-05 证据真实性的上限在哪里？

- **背景**：`test-report.json` 由 Agent 写，CLI 只能校验自洽。无法证明命令真的执行过。
- **选项**：
  - A. 接受"自证 + 自洽校验"（现状），在文档中明确"这是信任边界"。
  - B. 要求报告记录 `stdout_sha256`/耗时/环境（提高伪造成本）。
  - C. 提供 `df.py record-test`：由 CLI 执行命令并直接产出报告（Agent 不能伪造）。
  - D. 交付前人工抽检 1-2 条命令。
- **建议**：A 作为底线 + B（低成本）现在做；C 作为中期方向（会改变"谁执行测试"的协作方式）。
- **影响**：C 需要处理"测试需要 Agent 的环境/依赖"，可能不适用于所有技术栈。
- **阻塞**：影响 INV-023 的定性（从"未实现"变成"分层实现"）。

## D-06 `release` 门禁失败时是否应改状态？

- **背景**：`release` 在 blockers 非空时仍置 `release_candidate`（`df.py:2435`），随后返回 1。
- **选项**：
  - A. 不改状态（失败就停在原状态）。
  - B. 新增中间态 `release_generated`（报告已生成、门禁未过）。
  - C. 维持现状（"候选"只表示报告已生成）。
- **建议**：B（语义最清晰）；若不想加状态，A 次之。
- **影响**：改状态机会牵动 `release-ready` 的准入、看板、文档。
- **阻塞**：影响 INV-015 的目标迁移表。

## D-07 旧项目兼容边界保留到什么时候？

- **背景**：`legacy_release_shortcut`（`df.py:2573`）、`legacy_regression_accepted`（`df.py:2248`）、
  `release --legacy-regression`。示例项目本身就是 legacy 状态（schema 1.1）。
- **选项**：
  - A. 长期保留（有留痕即可）。
  - B. 设定"下一个大版本移除"，并在 `doctor` 里倒计时提示。
  - C. 立即移除（会打断现有项目）。
- **建议**：B（明确退出时间），并在 `doctor` 里把"legacy 项目"标为需要处理。
- **影响**：示例项目必须迁移，否则 CI 里的 doctor 会一直提示。
- **阻塞**：影响示例项目的处理方式（D-08）。

## D-08 示例项目怎么处理？

- **背景**：`examples/sample-project` 是 schema 1.1、accepted，但缺 `final-report.json`、
  `release-report.json`，用当前代码无法复现（见 F1）。
- **选项**：
  - A. 迁移它（补 JSON 报告/元信息/legacy 标记），让示例与当前门禁一致。
  - B. 用 `self-test` 生成新的示例，旧的移到 `examples/legacy/`。
  - C. 保持不动，只把它当"业务代码示例"，明确不属于交付门禁示例。
- **建议**：B（可信度最高），旧目录保留供历史参考。
- **影响**：改 `examples/` 会影响示例测试与文档链接。
- **阻塞**：影响"示例可信度"这项风险的关闭。

## D-09 并行执行用同工作区还是 worktree？

- **背景**：当前设计允许多 Agent 并行，但共享工作区让 Git 归属不可靠（B3）。
- **选项**：
  - A. 同工作区 + 主控显式确认"工作区其他改动"。
  - B. 每节点 worktree，主控合并（隔离好，流程重）。
  - C. 不支持并行（最保守）。
- **建议**：A 作为默认（配 D-03 的指纹归属）；B 作为"多 Agent 生产部署"的推荐。
- **影响**：影响 SKILL 的并行说明与部署文档，不影响核心 CLI。
- **阻塞**：影响 INV-010 的最终形态。

## D-10 是否拆分 `df.py`？

- **背景**：`df.py` 3574 行，28 个命令 + 门禁逻辑混在一起；每次安全修复要在多个入口补判断。
- **选项**：
  - A. 不拆，只加测试与收口函数。
  - B. 拆出 `dfstate.py` / `dfintegrity.py` / `dfpolicy.py`（见 07 第一节）。
  - C. 全面重构为命令对象体系（成本高，收益不确定）。
- **建议**：B（目标明确、可分批）；C 不做。
- **影响**：重构期间要保证 CLI 参数与输出不变，测试作为护栏。
- **阻塞**：不阻塞功能修复，但会影响 INV-008/015/017 的实施成本。

## 决策优先级

| 顺序 | 决策 | 理由 |
| --- | --- | --- |
| 1 | D-01 计划变更是否走 CR | 直接决定最严重绕过的修法 |
| 2 | D-02 需求基准指纹 | 与 D-01 一起构成"需求/计划不可暗改" |
| 3 | D-03 Git 归属 | 决定验收证据的可信度上限 |
| 4 | D-06 release 状态语义 | 决定状态机表怎么画 |
| 5 | D-05 证据上限 | 决定 INV-023 的定性与测试写法 |
| 6 | D-04 ignored 策略 | 与 D-03 一起完成"真实变更"闭环 |
| 7 | D-07 / D-08 兼容与示例 | 影响 CI 与文档可信度 |
| 8 | D-09 / D-10 部署与拆分 | 影响长期维护成本 |
